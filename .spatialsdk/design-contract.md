## 5. 不做清单（YAGNI 边界）

- 3D 蜡烛图 / `Stage` 沉浸方案 —— 已被用户明确否掉，不在任何版本目标里
- KDJ / RSI / BOLL 的真实指标计算 —— 本轮只做占位 UI（芯片可点、提示文字可显隐），真实计算是后续独立任务
- 分时 / 周K / 月K 切换后重新拉取对应周期的真实数据 —— 首版数据源仍是假数据，四个周期 Tab 本轮只做视觉选中态
  切换，图表内容不随周期 Tab 变化（只随 detailRangeChips 变化区间长度）
- 语音控制打开/关闭详情窗口、语音切换周期/指标 —— 语音识别引擎技术路径本身还没验证过（AGENTS.md 已记录），
  本轮详情窗口只做手势/点击入口
- 多个详情窗口同时打开 —— 同一时刻只保留一个，`WatchlistRow` 再次点击不同股票时复用同一个
  `WindowContainer`，通过 `bundle` 更新内容，不重新声明
- 详情窗口内的自选股增删/星标操作 —— 这些操作留在主窗口，详情窗口本轮不重复这些控件

# 契约增量 v2 — 主窗口分栏改版（2026-08-11，待用户确认）

## 0. 元信息

- 设计源：用户提供的 macOS 股市 App 截图（左侧列表+右侧详情分栏），以及用户对如何落地到本项目双窗口架构的
  口头说明（"主窗口默认为列表加详情页面，详情页面上有个按钮【新窗口打开】...长按列表对象也可呼出菜单
  【新窗口打开、置顶、移除】"）
- 视觉稿：https://claude.ai/code/artifact/35fb16fb-f02f-408b-bbe3-8db95d821a23（对照原图做了架构适配，不是
  照抄——原图是单窗口分栏，本项目仍是"主窗口+可选独立详情窗口"的双窗口架构，只是把详情**预览**嵌进了主窗口）
- **架构没有变**：`DefaultWindowContainer` 还是唯一常驻窗口；`DetailWindow`（`WindowContainer` id
  `DETAIL_WINDOW_ID`）还是独立弹出窗口，只是触发方式从"点击列表行自动弹出"改成"按钮/菜单显式触发"

## 1. 架构与交互变化（本增量的核心，需要你确认）

1. **主窗口从纯列表变成左右分栏**：左侧 `mainListPane`（约 400dp 宽，内容基本不变：编辑/搜索/表头排序/
   星标/迷你走势线）+ 右侧 `mainDetailPreview`（新增，约占剩余宽度）。分栏容器仍是同一个
   `DefaultWindowContainer`，不是新窗口，也不是 `Subwindow`。
2. **点击列表行的行为改变**：原来"点击行名→关闭已开的详情窗口→重新 openWindowContainer 弹出新窗口"，
   现在改成"点击行→只是把该行设为 `selectedCode`→右侧 `mainDetailPreview` 显示该股票的**轻量预览**"，
   不再自动弹窗口。默认选中列表第一行（对齐参考图"默认选中第一项"的行为），列表为空则显示空态提示。
3. **`mainDetailPreview` 只放"一眼看懂"的内容，不是完整详情**：股票名+代码+交易所、价格+涨跌幅、3档区间
   芯片（沿用现有"近1月/近3月/近1年"，**不采用**参考图的 11 档时间粒度——我们只有日线收盘数据，做不出
   分时/周线/年线的真实区别，硬做会是假数据）、简化K线（只叠加 MA5/MA10，**不含** VOL/MACD/KDJ/RSI/BOLL
   那 5 个指标——完整指标体验保留在独立详情窗口里，避免同一份重型图表逻辑在两个地方各维护一份）、一个
   "在新窗口打开"按钮、一个"关键指标"网格（见下面第 2 节）。
4. **"在新窗口打开"按钮**：点击后调用现有的 `navigator.openWindowContainer(DETAIL_WINDOW_ID, DETAIL_WINDOW_TAG, bundle)`
   逻辑（`WatchlistScreen.openDetail()` 已有，直接复用），弹出独立 `DetailWindow`，内容还是现在这套完整的
   K线+8个指标芯片+MACD/KDJ/RSI面板，**这部分完全不改**。
5. **长按列表行 → 呼出上下文菜单**：用真实存在的 `Menu`/`MenuItem`（`com.pico.spatial.ui.design.menu`，已
   读源码确认）锚定该行弹出，配合 `detectTapGestures(context, targetedToEntity=null, onLongPress=..., onTap=...)`
   （`com.pico.spatial.ui.foundation.gesture.ComposeTapGestureDetectorExt`，已确认存在于本项目实际使用的
   spatial-ui-foundation 0.13.3，不是凭空发明的 API；两个手势回调写在同一个 `pointerInput` 块里，符合
   `spatial-sdk-guideline` "不要在同一个 pointerInput 里叠多个 detectSpatial* 识别器"的规则）。菜单三项：
   - **新窗口打开** — 效果同第 4 条，从列表行直接触发，不需要先点选中
   - **置顶** — 新功能，见第 3 节说明
   - **移除** — 复用现有的删除确认 `AlertDialog`，不是无确认直接删（破坏性操作要二次确认，这条规则不变）

## 2. 关键指标网格 — 字段把握程度分级（如实标注，不承诺做不到的）

参考图的字段里，免费源（Eastmoney）**大概率能拿到、需要在实现阶段用 curl 核实具体字段码**：

| 字段 | 把握 | 来源思路 |
|---|---|---|
| 今日开盘价 / 今日最高价 / 今日最低价 | 较高 | 扩展现有 `EastmoneySource.fetchQuote` 请求的 `fields` 参数 |
| 成交量 | 较高 | 同上 |
| 平均成交量 | 中 | 客户端从 kline 历史里的成交量字段算平均，需要先扩展 kline 解析（现在只取了收盘价，见 AGENTS.md"已知简化"） |
| 市盈率 / 52周最高价 / 52周最低价 / 市值 | 中 | 可能要加请求字段甚至换一个 Eastmoney 接口，具体字段码没有当场验证过，不确定 |

**大概率免费源没有、直接如实显示"—"**（参考图本身对 Dow Jones 这个指数也是这么处理的，不是我们没做，是
数据/概念本身不适用或源没有）：贝塔系数、收益率、每股收益。

如果实现阶段发现"中把握"那四项确实拿不到，会退化成"—"，不会拿假数据凑数。

## 3. "置顶"语义（需要你确认的产品判断）

点击"置顶"后：

1. 把该股票的 `orderIndex` 设成当前最小值 − 1（排到默认顺序最前）
2. **同时清除表头排序**（`sortKey = null`），否则如果用户正在按"价格"或"涨跌幅"排序，置顶操作不会带来任何
   肉眼可见的位置变化，会显得"点了没反应"

第 2 条是我的判断，不是你原话里明确要求的，需要你确认是否符合预期，还是你想要"置顶只影响默认顺序，激活的
排序不受影响、也不清除"（这样的话点了置顶但排序还在时，效果确实看不出来，需要你确认这是否可接受）。

## 4. 不做清单（本轮新增）

- 不采用参考图的 11 档时间范围 tab（1天/1周/1个月/3个月/6个月/年初至今/1年/2年/5年/10年/全部）——继续用
  现有 3 档
- `mainDetailPreview` 不含完整的 8 个指标芯片，只固定叠加 MA5/MA10——完整指标切换只在独立详情窗口里
- 不会为了填满参考图的指标网格而编造/估算贝塔系数、收益率、每股收益——免费源没有就显示"—"
- 长按菜单不做多级子菜单（`SubMenu`）——三个平级菜单项够用，不需要

## 1. 与契约文字的偏离（一处，主动记录）

- **日期不是独立数组**。v3 变化清单写的是"新增日期数组（`RemoteStock.dates`/`Stock.dates`）"，实现改成
  让日期随 `Candle.date` 一起走（`RemoteStock.candles`/`Stock.candles`）。理由：X 轴日期标签必须和蜡烛
  严格一一对应，而区间切片（`takeLast(n)`）作用在两个平行数组上时，任何一次只切一边的改动都会让日期和
  蜡烛错位，且这种错位不会报错、只会静默显示错误日期。放进同一个对象里，切片天然对齐。功能上完全满足

## 2. §2.5/§2.6 字段核实的真实结果

契约要求"实现阶段用 curl 核实字段码"。核实做了，结果和契约的预期不同：

  **字段码和缩放倍率都没能核实**，UI 里一律显示"—"，没有猜倍率。

## 3. 实施期发现的既有缺陷（超出 v3 范围，但必须修才能兑现 v3）

- **kline 解析一直丢掉真实 OHLCV 和日期**。接口本身返回 `date,open,close,high,low,volume,amount`
  （注意收盘价在高/低之前），旧代码只取了 index2 收盘价，再用 `buildCandles()` 二次合成 OHLC。v3 要求
  "成交量面板标题栏显示最新成交量数值"，而合成的 volume 是
  `abs(close-previous)*40+30+(index%5)*6`——把它当真实成交量报出去会直接违反契约自己"不拿假数据凑数"的
  原则。所以顺带把解析改成取真实 OHLCV+日期（这也闭环了 AGENTS.md「下一步 #8」）。
- **`lmt` 参数一直是无效的**：带显式 `beg`/`end` 时会被静默忽略（实测 `lmt=4` 返回全部 5980 行）。
- **`fqt=1` 在早年历史上给出负价**（600519 的 2001 年行是 `-312.68`），一行就能把价格轴拽走。
- **AGENTS.md 里"kline 取多日真实历史"这条从未被实证**：当初被截图验证的是**报价**接口。门禁 B 截图里

- 新增一条硬规则并落进代码：**合成数据不得以数字形式呈现**。蜡烛/柱可以是合成形状（占位图形），但任何
  精确数字必须有真实来源——所以没有真实 K 线时，成交量面板标题、基本参数网格、K 线极值标注一律"—"或

## 6. v3 之后的增量裁决（2026-08-11，用户直接指令）

### 裁决四：周K/月K 做真实聚合，作废 §3 不做清单第 3 条

用户原话："切换日K、周K、月K时没有反应"。§3 把它列进不做清单是**当时**的正确选择（没有真实历史数据），
但现在新浪日线链路已经稳定给到 230 根，聚合就是纯本地计算，没有理由继续留一个点了没反应的 Tab。

实现口径（通达信/同花顺，`data/StockMath.kt` 的 `KPeriod` + `aggregateCandles`）：

| 字段 | 取值 |
|---|---|
| 开 | 区间内第一根的开盘 |
| 收 | 区间内最后一根的收盘 |
| 高 / 低 | 区间极值 |
| 量 / 额 | 求和 |
| 日期 | 区间内**最后一个交易日**（本周/本月未走完时，末根就是一根正在形成的 bar） |

分组键只用日期里天然带的信息，不查节假日表：周线按 **ISO 周**（`WEEK_BASED_YEAR` + `WEEK_OF_WEEK_BASED_YEAR`，
不能用 `date.year`，否则 12 月底会和一月初劈成两根），月线按 `yyyy-MM`。

**区间档位 × 周期的换算**：`barsFor(交易日数) = ceil(交易日数 / 每根覆盖交易日)`，日线 1、周线 5、月线 21。

| | 近1月(22) | 近3月(66) | 近1年(220) |
|---|---|---|---|
| 日 K | 22 根 | 66 根 | 220 根 |
| 周 K | 5 根 | 14 根 | 44 根 |
| 月 K | 2 根 | 4 根 | 11 根 |

**刻意不做"至少 N 根"的下限兜底**——那等于悄悄把"近1月"画成两个月，档位标签就成了假的。上表最窄的
"近1月 + 月K"是 2 根，仍然能画；真的退化到不足 2 根时（新股）由图表区给一行提示，**不放宽区间**。

**两条必须守住的边界**：

1. **"今日"字段只能取日线末根**。头部涨跌幅、基本参数网格的今开/最高/最低/成交额描述的是今天这一天。
   周期序列末根在月K下是整月的开高低量额，拿它填"今开"就是把本月数字标成今天的。`DetailScreen` 里
   `latestDaily` 和 `candles` 是两条独立的线。
2. **整屏兜底只看日线够不够**。周期/区间选择器都排在图表下方，如果拿聚合后的根数去判、然后 `return`
   整个 Column，用户就被锁在那个组合里切不回来了。不足 2 根只让图表区给提示。

**验证**：`AggregateCandlesTest`（7 例，锁 ISO 周跨年 / 无日期不聚合 / 日线恒等 / barsFor 取整）+
门禁 B 第 11 轮截图（`gateB-r11-dbg-state.png`：`DBG p=2 r=2 n=11 d=230 per=Monthly`，11 根粗月线，
极值标注 **1151.01** 与离线 Python 复算的 2026-06 月线最低价逐位一致，M20 因只有 11 根正确显示"—"）。

### 裁决五：K 线支持横向拖拽平移

用户原话："当前K线图无法进行横向拖拽滚动"。§3 不做清单里排除的是"K线图的缩放/平移**按钮排**"（同花顺那排
«+−‹›⤢），拖拽手势本身不在排除范围内，这里补上。

- 可见窗口 = 整条周期序列上的一个滑动切片：宽度由区间档位定，位置由拖拽定。向右拖 = 露出更早的历史。
- **手势必须走 `detectSpatialDragGesture`**（`com.pico.spatial.ui.foundation.gesture`）。真机实测：
  头显交互是 `GAZE_PINCH`（眼动注视 + 捏合），2D MotionEvent 的 x/y 就是**注视点**、捏合拖拽时几乎不动，
  位移只在 3D 字段里；`ScrollEvent3D` 有效 0 次、`DragEvent3D` 有效 23 次。所以
  `detectHorizontalDragGestures`（2D touch slop）和 `Modifier.scrollable` 都收不到——这两版都装到真机上
  被否掉过。详见 AGENTS.md "头显的输入是 GAZE_PINCH"。
- 状态在 `content/ChartPan.kt`：偏移以 **bar** 为单位；不足一根的像素余量要累积（否则慢拖每次被
  `toInt()` 抹成 0，永远不动）；两端夹紧。
- 一根 bar 的像素宽度由 `KLineChart` 在绘制时通过 `onSlotWidth` 回填——几何只有一份，避免调用方在外面
  重算 padding 造出第二份迟早对不上的几何。回填目标必须是普通 var，不能是 snapshot state（绘制期写
  snapshot state 会绘制→重组→再绘制地自激）。
- 归零的 key 只有"标的/周期/区间"，**不含数据序列**——否则每次轮询换一个新 list，用户正翻着历史会被
  定时弹回最右端。
- **手势必须写成不捕获组合期局部值**（`pico-sdk-compose-pitfalls` 陷阱 1：SDK 手势只保留首次传入的
  lambda）。所以状态收进一个身份稳定的 `ChartPan` 对象、回调在触发时刻读，`pointerInput` 的 key 固定 `Unit`。

**验证到什么程度（如实）**：`ChartPanTest` 8 例覆盖方向/亚根余量累积/两端夹紧/序列比窗口短时 no-op/
除零/reset 清余量/组合期只读夹紧。但**"SDK 会不会把拖拽事件送到这个 Box"没法用截图自证**——
`adb shell input swipe` 注入对 spatial 面板无效（拖前拖后两张截图 `md5` 完全一致，连射线光标像素都没变）。
这一条要真机上手确认。

# 契约增量 v6 — 详情窗口默认摆放位置（2026-09-20，已确认并实施完毕）

## 0. 元信息

- 触发：用户原话"默认打开新个股详情窗口在主窗口的右侧（作为预览）"
- 设计源类型：文字指令（无视觉源；本增量只改窗口在空间里的落点，不改任何面板内部排版）
- 影响文件：`Main.kt` 一处（`WindowContainer` 声明新增 `placement` 参数）。
  `DetailScreen` / `WatchlistHost` / manifest **均不改**。
- 契约版本：v5 → v6

## 1. API 核实结果（改之前先确认这条路走得通）

已核实，三条都基于 0.13.3 真实源码，不是猜的：

| 事实 | 证据 |
|---|---|
| `openWindowContainer(id, tag, bundle)` **没有**位置参数 | `agent-vault/.../open-or-close-a-windowcontainer.md`；核实版本 6.0.0 文档 |
| 位置控制在**声明侧**：`WindowContainer(..., placement: (PlacementContext.() -> Placement)? = null)` | `foundation-0.13.3-sources.jar` → `dsl/WindowContainer.kt:109` |
| `Placement.right(anchorContainer, offset)` 等五个工厂方法 | `foundation-0.13.3-sources.jar` → `dsl/Placement.kt` |

`placement` lambda 在**每次新实例创建时**求值，receiver `PlacementContext` 提供
`containers: List<ContainerProxy>`（当前所有已开窗口，带 `id`/`tag`/`state`），所以锚点可以动态挑。

**能力边界（写进契约，免得以后再问）**：只有相对锚点的上/下/左/右四个正交方向 + 一个 `Dp` 偏移。
没有绝对世界坐标、没有朝向角、没有深度距离。窗口**开出来之后不能再移动**——运行时的
`WindowContainerParamsUpdater` 只有 `setResizeRestriction`/`setVolumeBasePanelType`/`setCaptionBarType`。

## 2. 本增量的行为定义

| 元素 id | 旧行为 | 新行为 |
|---|---|---|
| detail 窗口落点 | 未指定（`placement` 为 null，系统自行决定，实测出现在正前方） | 锚定主窗口右侧 |
| detail 窗口尺寸 | 680×660dp（裁决七） | **不变** |
| detail 窗口内容 | `DetailScreen(code)` | **不变** |
| 同 tag 复用 | 已开窗口被拉到前台 | **不变**（复用路径不重新求值 placement，位置保持用户拖动后的样子） |

锚点识别：主窗口是 `DefaultWindowContainer`，manifest metadata 里
`pico.spatial.windowcontainer.id = "YourPlanarWindowContainer"`。
实现时**不写死这个字符串**，改用"`containers` 里 id != `DetailWindow` 的那个"来取，避免以后改 manifest 时静默失配。

## 3. 多个详情窗口怎么排 —— 用户已裁决：方案 B（2026-09-20）

裁决八（2026-08-11）明确"不同股票各自一个窗口，可并排比较"。如果每个窗口都锚定主窗口右侧，
第二个会**落在第一个的同一位置上**，把它盖住。两种方案：

- **方案 A — 全部锚主窗右侧（严格按字面）**：每个新窗口都出现在主窗口右边同一处，后开的盖住先开的，
  用户自己拖开。好处是"预览位"永远固定、可预期；坏处是裁决八的"并排比较"要靠手动拖拽才能实现。
- **方案 B — 首个锚主窗右侧，后续向右瀑布**：第一个贴主窗右边；之后每个贴在**最后一个已开详情窗**右边，
  自动排成一行。既满足"默认在主窗口右侧"，也兑现裁决八的并排比较，不用手动拖。

**裁决：方案 B。** 用户 2026-09-20 通过选项确认。落点规则写死为：

```
anchor = containers 里【第一个】 id == "DetailWindow" 的实例
       ?: containers 里【第一个】 id != "DetailWindow" 的那个（= 主窗口）
placement = Placement.right(anchor)      // offset 用默认值，见 §5
两者都取不到 → Placement.none()          // 退回系统默认，不崩
```

⚠️ **取 `first` 不是 `last`，这点极易写反。** `PlacementContext.containers` 不是按打开顺序排的，
是**按焦点排序、最近获得焦点的在最前**。证据：`core-0.13.3-sources.jar` →
`SpatialContainerManager.OrderedUniqueList.items() = map.values.toList().asReversed()`，
配合 `ensure(..., makeMostRecent)` 与 `access()`，以及源码原注释
"Insert as the least-recent so that items() (reversed) keeps focused containers ahead of
newly created/background containers"。写成 `lastOrNull` 会锚到**最久没碰过**的那个详情窗。

由此派生的一条行为（可接受，记录在案）：新窗口是从主窗口点出来的，点的瞬间主窗口持有焦点，
所以 `first { DetailWindow }` 取到的是**用户最后一次交互过的那个详情窗**。如果用户先回头点了详情窗 A、
再从主窗口开 C，C 会落在 A 右边而不是最右端。语义上是"出现在你刚才在看的那个旁边"，不算 bug。

调用时机：`beforeSettingPlacementConfiguration` 在新容器的参数构建**之前**求值
（`SpatialContainerApis.kt:389`），所以 `containers` 里**不含**正在创建的这一个。

同一只股票再点一次走 tag 复用路径，**不重新求值 placement**，窗口停在用户上次拖到的地方。

## 4. 不做清单（本轮新增）

1. 不做绝对坐标摆放、不做朝向角、不做距离控制 —— SDK 不提供（见 §1 能力边界）。
2. 不做"窗口开出来之后自动重排/吸附" —— SDK 无运行时移动 API。

4. 不给主窗口加 placement（它是启动窗口，没有锚点可依）。

## 5. 已知的不可验证项（提前声明，不要事后当成"验证通过"）

- `offset` 参数的 KDoc 只说"从原始对齐位置的偏移"，**沿哪个轴、正负方向是什么没有文档**。
  本轮先传默认值 `Dp.Unspecified`（让系统给默认间距），不猜 offset 数值。

  这个工具给不了可靠反馈。门禁 B 能证明的只有"两个窗口都开出来了、内容正常、没崩溃"；
  "确实在右侧、没有重叠"这条**只能上真机确认**，本轮会如实标为不可判定。

## 2. 窗口左右均匀分布

规则（用户只说"均匀分布在左右两侧"，以下具体规则由实现方定，需你过目）：

```
side   = 左右两侧当前窗口数较少的一侧；相等时取右侧
anchor = 该侧【最外侧】的那个详情窗；该侧为空 → 主窗口
placement = Placement.placement(anchor, orientation = side)
```

关掉中间任意一个窗口后计数自动变化，下一个新窗口会补到较少的那侧，**自动重新平衡**。

## 3. ⚠️ 这套方案依赖应用自己记账 —— SDK 没有查询 API（已核实）

| 想要的能力 | SDK 有没有 | 证据 |
|---|---|---|
| 列出当前已开的 WindowContainer | **没有** | `SpatialNavigator`（`platform-0.13.3-sources.jar`）只有 `openWindowContainer` / `closeWindowContainer` / `minimizeWindowContainer` / `restoreWindowContainer`，无任何查询方法 |
| 查询某个 id+tag 是否已开 | **没有** | 同上 |
| 当前容器的状态 | 有，但只有自己这一个 | `SpatialContainerStateManager` 只暴露 `isFocused` / `isOnstage` / `isSighted` |
| 创建新窗口时看到所有已开窗口 | **有，但只在 placement lambda 里** | `PlacementContext.containers` |

所以新增进程内单例 `DetailWindowRegistry` 记账：

- **注销**靠详情窗口内容里的 `DisposableEffect(code) { onDispose { unregister(code) } }`——
  用户从系统标题栏关掉窗口时，该容器的 Activity 销毁、composition 释放，`onDispose` 触发。
- **对账**在 placement lambda 里做：那里的 `containers` 是权威快照，每次新开窗口时拿它校正账本，
  能自愈漏掉的注销。

### 已知风险（如实记录，不掩盖）

`onDispose` 不是万无一失的：已知 `pico-cli app stop` 是强杀、`onDispose` 一行不跑（AGENTS.md 有记录），
但那种情况整个进程连同账本一起没了，不会留下脏数据。真正的残留风险是"窗口关了但 `onDispose` 没跑"，
后果是：点那只股票会被当成"已开窗"而只做拉前台，实际没有窗口可拉，表现为**点了没反应**。
placement lambda 的对账只在"有新窗口被创建"时才发生，所以这种残留可能要等下一次开别的窗口才自愈。
本轮接受这个风险，不为它加轮询或额外的生命周期监听。

## 4. 同 tag 复用会重算 placement —— 拉前台必须显式返回 none()

已核实：`Context.openWindowContainer` → `SpatialContainerManager.openWindowContainer` →
`SpatialContainerApis.openSpatialContainer` → `toSpatialContainerParams(tag)`，而
`beforeSettingPlacementConfiguration` 就在 `toSpatialContainerParams` 里被调用
（`SpatialContainerApis.kt:389`）。**即每次 open 调用都会重新求值 placement，包括同 tag 复用那次。**

placement lambda 拿不到正在打开的那个窗口的 tag，所以由应用在调用前置一个 `pendingIsReuse` 标志，
lambda 见到它就返回 `Placement.none()`，避免把用户已经拖到别处的窗口拉回原位。
